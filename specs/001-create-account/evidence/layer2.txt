Scenarios proved
----------------
- Student persistence: every column read back through profego_pdo(); rol
  estudiante, estado activo, non-null fecha_registro, lowercase email,
  digits-only phone, Cedula/ID as typed, normalized name and lastname.
- Password confidentiality and round trip: stored hash is non-empty, differs
  from the plaintext (TEST_PASSWORD), verifies the correct password and rejects
  a wrong password (WRONG_PASSWORD).
- Tutor persistence: one account plus one perfiles_docente row with
  estado_verificacion = pendiente, calificacion_prom numeric 0.00 and
  total_tutoria 0, in the same transaction.
- Duplicate pre-checks: email, phone and Cedula/ID separately and all three
  combined, each returning exactly one exact Spanish message per duplicated
  field with unchanged row counts.
- Case-insensitive uniqueness: uppercase email and uppercase/default Cedula/ID
  variants are detected as duplicates (behavioral proof of RF-6 uniqueness).
- Unique-collision path: a direct register_account() call bypassing the
  pre-check raises SQLSTATE 23000; the service rolls back, re-checks and
  returns the same three duplicate messages with no partial row and no open
  transaction.
- Atomicity: the CLI-only fail_tutor_profile seam throws after the account
  insert; neither the account nor a tutor profile remains, and no transaction
  is left open.
- Collation: usuarios.documento uses a utf8mb4 case-insensitive (_ci)
  collation. The database default is utf8mb4_unicode_ci, while the column's
  actual value is utf8mb4_general_ci because the shipped tables inherit it
  from DEFAULT CHARSET=utf8mb4. No schema change was made. This is recorded
  as an environmental finding; case-insensitive uniqueness is proved
  behaviorally by the duplicate scenarios above.
- SQL injection: the allowed-character payload
  "O'Brien' OR 'a' LIKE 'a'--" (26 characters) is stored literally, read back
  literally through both the raw application PDO path and the application
  account helper, and leaves an unrelated account row byte-for-byte
  unchanged.

phone and Cedula/ID derived from it. All created identifiers were captured.
Cleanup ran in a finally block, deleting perfiles_docente rows before usuarios
rows for each captured set (set 2 deleted 1 profile then 1 account). Residue
was asserted by captured identifiers only: 0 for every set, 0 total, and row
counts returned to baseline. Tables were never truncated and no universal
prefix was used.

The single remaining usuarios row is the pre-existing all-empty prototype
residue row. It was not read for assertions, modified, or deleted.
